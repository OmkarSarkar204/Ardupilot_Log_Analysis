# ArduPilot Log Failure Diagnosis Prototype (V-3)

The Latest Version of the Log Diagnosis Engine: This prototype analyzes ArduPilot flight logs (.BIN) and automatically identifies possible root causes such as motor failure or battery issues using telemetry features and a machine learning model.

## Current Capabilities

The current prototype can:

* Parse ArduPilot .BIN logs using pymavlink  
* Extract telemetry signals (ATT, BAT, RCOU)
* Compute mechanical and power features  
* Detect anomalies in flight behavior  
* Train a machine learning classifier from labeled logs  
* Identify potential root causes (motor or battery failure)  
* Generate a timeline of detected anomalies

## System Architecture

The analysis pipeline consists of stages like:

1. Log Parsing  
2. Feature Extraction  
3. Dataset Generation  
4. Machine Learning Model  
5. Physics Validation  
6. Event Fusion/clustering and Diagnosis

### Log Parsing

The parser reads ArduPilot .BIN logs using pymavlink and extracts telemetry messages including:

* ATT: attitude data  
* BAT: battery telemetry  
* RCOU: motor output signals  

It also identifies which servo channels correspond to motors as different users have different channels alloted (like 33–40). (https://ardupilot.org/copter/docs/common-rcoutput-mapping.html#default-values)

### Physics Engine

* The physics engine converts raw telemetry signals into a unified flight timeline.
ArduPilot logs contain asynchronous telemetry streams:

* `ATT ~50Hz`
* `RCOU ~50Hz`
* `BATT ~10Hz`

These are synchronized using time-alignment and the result is a single dataframe representing the entire flight timeline.

### The physics engine computes diagnostic features that describe the physical behavior of the vehicle.

* Motor Spread: measures imbalance between motor thrust commands.

  `motor_spread = max(motor_pwm) - min(motor_pwm)`

(A large spread indicates one or more motors are compensating for thrust loss elsewhere.)

* Roll Error: measures the difference between the commanded roll and the actual roll.

  `roll_error = |desired_roll − actual_roll|`
  
(Large roll errors indicate the controller is unable to stabilize the vehicle.)

* Voltage Sag: measures instantaneous voltage drop relative to maximum observed voltage.
  
  `volt_sag = V_max − V_current`

(Large sag events often indicate battery collapse or excessive current draw.)

Similarly all the required features will be calculated for different vehicles to check their Physical State.

### Feature Extraction

From the raw telemetry the system computes diagnostic features:

* motor_spread
* roll_error
* volt_sag
* power_watts

Additional features include rolling averages and voltage sag trends.

The model predicts likely anomaly types such as motor or battery issues (due to limited features and will extend to add anomalies).


### Physics Validation

The physics validator performs independent rule-based checks using statistics.

Examples include:

* motor thrust imbalance detection

* abnormal voltage sag detection

* excessive roll error

Thresholds are calculated dynamically from flight baseline statistics.
This helps confirm whether a detected anomaly is physically plausible (This is basically acting like a check engine).

Physics rules detect physical threshold violations while the ML model detects telemetry patterns associated with known failures.
Agreement between the two detectors increases confidence in the diagnosis.

### Event Detection

Detected anomalies are grouped into continuous time windows representing events (Event Clustering and not as separate events).
Short transient spikes are filtered to reduce noise.

* How it works internally:
if it detects:
Motor imbalance
```
Start: 12.0s
End: 15.5s
Duration: 3.5s 
```

Consecutive anomaly detections are merged into continuous time windows.

### Diagnosis

The diagnostic engine compares ML predictions and physics-based detections across the timeline.
Example working:

```
If battery voltage collapses:
  then motor thrust reduces and attitude becomes unstable.
```

# Limitations of the Current Prototype

Dynamic thresholds assume that early flight data represents healthy behavior. Not True always,
If a vehicle begins the log with a fault, the baseline estimation may be inaccurate.

### Modeling Limitations

The current Random Forest model evaluates individual rows independently.

It does not capture patterns such as:
*	oscillations
*	degradation trends
* vibrations

### Limited Dataset

The prototype was trained primarily on ~15 SITL-generated logs.
Robust generalization requires a larger dataset of real flight failures.

### Limited Sensor Coverage

Current analysis focuses on a small set of derived features.

Future versions should incorporate majority signals including:
*	VIBE vibration logs
*	GPS consistency metrics
*	IMU clipping detection
*	ESC telemetry

### Multi-Vehicle Support

The architecture is designed to support multiple vehicle configurations.

## Parameter Extraction

Vehicle type can be inferred from parameters such as:

Vehicle-Specific Diagnostics: Different vehicle types require different failure logic.

Examples:

## Evolution of the System

### Version 1
A simple physics-based anomaly detection engine.

Features:
- log parsing (Hardcoded motor pins(c1-c4), crashed while testing on a real log)
- asynchronous telemetry handling
- dynamic hardware profiling
- motor imbalance detection

### Version 2
Hybrid system combining physics checks and machine learning classification.

Additions:
- dataset builder
- RandomForest classifier
- battery failure detection

### Version 3
Event based system.

Improvements:
- structured anomaly timelines
- separation of detection and diagnosis stages
- extensible architecture
